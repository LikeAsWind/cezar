# Global Workspace and Project UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make Cezar start as a project-neutral global workspace, require an explicit registered project for every project operation, and present an IntelliJ IDEA-style workspace/project UI.

**Architecture:** `cez serve` will construct a workspace-level runtime only. Every repository runtime will be created through the existing `ProjectContexts` registry factory using an explicit `projectId`; the HTTP surface will keep workspace routes unscoped and expose project routes only under `/api/v1/p/:projectId`. The SPA will treat the URL as the only active-project source, keep global and project query keys distinct, and render one persistent shell whose project section appears only below `/p/:projectId`.

**Tech Stack:** TypeScript 7, Node.js 20+, Hono, Zod, React 19, React Router 7, TanStack Query 5, Tailwind CSS 4, Vitest, Testing Library, e2e runner.

**Spec:** `docs/superpowers/specs/2026-10-14-global-workspace-project-ui-design.md`

## Global Constraints

- `/` is always the global workspace home and never redirects to a recent, boot, or default project.
- `cez serve` must not register, open, recover, or otherwise use `process.cwd()` as a project.
- Project operations require a registered `projectId`; no process-global mutable current project is introduced.
- `/api/v1/...` remains workspace-level; project APIs use `/api/v1/p/:projectId/...`.
- `/p/default` is compatibility-only, never generated by new UI, and may resolve only when the registry yields one unambiguous project.
- A zero-project workspace is a normal, usable state.
- Existing project data remains under `<project>/.ai/cezar`; this change does not migrate run state.
- Every request and response shape remains a Zod schema in `packages/contract`, and Hono routes remain chained with middleware validation.
- One workspace-wide `WorkspaceSemaphore` remains shared by every lazily built `RunManager`.
- Project removal disposes only that project's runtime; leaving a project route never stops its background tasks.
- `cez run` continues to use its explicit `--repo` or current-directory target.
- No new required configuration or default-project setting is added.

- [x] **Step 3: Add the system runtime boundary**

```ts
export interface SystemRuntimeDeps {
  listProjects?: typeof listProjects
  semaphore?: WorkspaceSemaphore
  workspaceEvents?: WorkspaceEventBus
  providerAuth?: ProviderAuthService
  providerRuntimeAuth?: ProviderRuntimeAuthObserver
  contexts?: ProjectContexts
}

export interface SystemRuntime {
  semaphore: WorkspaceSemaphore
  contexts: ProjectContexts
  workspaceEvents: WorkspaceEventBus
  providerAuth: ProviderAuthService
  providerRuntimeAuth: ProviderRuntimeAuthObserver
  start(): Promise<void>
  dispose(): void
}

export function createSystemRuntime(deps: SystemRuntimeDeps = {}): SystemRuntime {
  const semaphore = deps.semaphore ?? new WorkspaceSemaphore()
  const workspaceEvents = deps.workspaceEvents ?? new WorkspaceEventBus()
  const providerAuth = deps.providerAuth ?? new ProviderAuthService({ cwd: cezarHomeDir() })
  const providerRuntimeAuth = deps.providerRuntimeAuth ?? new ProviderRuntimeAuthObserver(
    providerAuth,
    (status) => workspaceEvents.emit('provider-status', status),
  )
  const contexts = deps.contexts ?? new ProjectContexts({
    listProjects: deps.listProjects ?? listProjects,
    semaphore,
  })

  contexts.onStoreCreated((store) => providerRuntimeAuth.watch(store))

  return {
    semaphore,
    contexts,
    workspaceEvents,
    providerAuth,
    providerRuntimeAuth,
    async start() { await semaphore.refresh() },
    dispose() { contexts.disposeAll() },
  }
}
```

Keep `ProjectContexts.build()` responsible for `RunStore.open`, `AutomationStore.open`, recovery, worktree pruning, retention, launch key creation, and repository arming. Remove comments and branches that describe a separately constructed boot context.
