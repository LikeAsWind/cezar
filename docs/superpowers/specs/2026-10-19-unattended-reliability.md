# 无人值守工作流可靠性补强

依据：用户要求在当前对话把已审查的六项问题建立任务，依次完成。

1. 宿主保存可信验证计划和验证凭证；工作树中的副本变动不能降低检查门槛。这里防止误改，不宣称在同一操作系统账号下隔离恶意代码。
2. 成功 verdict 必须有对应阶段的有效产物；问题编号、提问来源和裁决返回目标由宿主核验。缺失或不一致时走已有失败出口，不新增模型角色。
3. 修 Bug 的已知基线失败可显式记录和分类；未知、环境或不符预期的失败保持阻塞。最终验证不接受预期失败。
4. 对该受管工作流，阻塞后 Continue 应恢复原工作流而非仅开启聊天。保存恢复位置和问答上下文，保留快照及回路预算；不改变普通工作流 Continue。
5. 复杂度决定审查强度，执行方式同时取决于任务独立性和实际能力。有独立子任务与可用派发能力才使用 SDD；否则使用 native 并说明理由。无能力时不能伪造派发。
6. 同一调用方澄清后优先继续自己的会话；独立设计/代码审查使用独立上下文。后端不支持恢复时回退到文件恢复。

不修改原始 Superpowers vendor 提示词；只修改本地编排、共享约束和宿主保障。保持零配置与普通工作流行为，保留用户现有未提交修改。单项先写回归并观察失败，再实现和验证；不自动提交、推送或合并。
