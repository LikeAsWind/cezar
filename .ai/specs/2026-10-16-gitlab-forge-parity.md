# GitLab forge parity

## Approved goal

GitLab projects must expose the same existing cezar workflows as GitHub projects, including GitLab Self-Managed. The motivating repository is `git@new-gitlab.yiyaowang.com:search-yc/yc-sale-control-server.git`, registered locally as `yc-sale-control-server`, with current branch `master`. Do not modify that application's repository while implementing cezar support.

## Current evidence

- `server/forge/index.ts` recognizes only `github.com`; `ForgeKind` and the project registry contract's `forge` accept only `github`. `forgeInfoSchema` also still defines that literal, but is NOT referenced by `healthResponseSchema`: workspace health has no `forge` field.
- `server/server.ts:healthSnapshot` deliberately omits the deprecated project-bound `forge`, `repoRoot`, `repo` and `bootProject` fields. `server/health-forge.test.ts` repeatedly asserts `body.forge === undefined`. The local object in `web/src/routes/task-git/run-git-step.tsx` still hard-codes `kind: 'github'`; it is not evidence that health sends a forge.
- `git-remotes.ts:parseRemote` retains only the last two path components. GitLab nested groups therefore lose their namespace; `server/forge/index.test.ts` explicitly pins that existing behavior. Full-path support requires a deliberate parser contract change and consumer audit, not merely a new driver.
- `ForgeDriver` covers detection (including cached detection), issue/PR lists, search, recent creations, draft creation (`createPR`), branch PR lookup (`prStatus`), merge state, merge, diff and web URL construction (`viewUrl`). It lacks comments, checks, reference-status batches, PR updates and issue/PR comments as driver methods.
- `server/server.ts` bypasses the driver for lists (`fetchGithub`), comments (`fetchGithubComments`), checks (`fetchGithubChecks`), reference status (`fetchGithubRefStatus`), changes (`fetchGithubPrDiff`) and task PR creation (`createDraftPr`, despite existing `createPR`). Only the merge-state and merge routes in that family already call `resolveForge`.
- `workflows/run.ts` has five GitHub-specific nodes to adapt: `github.draft-pr`, `github.pr-comment`, `github.pr-update`, `github.issue-comment` and `github.wait-ci`. Their calls bypass the driver for creation, comments, updates and checks.
- `automations/github-poller.ts` directly runs `gh` for polling; `automations/pr-head.ts` separately runs `gh` for PR-head metadata. These are a poller and a checkout helper, not two poller implementations. Both need provider routing; adding a driver alone leaves these flows unsupported.
- Sidebar, command palette and repository branches gate features on `forge === 'github'`. Task reference parsing and links also need platform-aware review.
- The dashboard already resolves `ForgeDriver.recentCreated`, but labels and error messages assume GitHub.
- `glab.exe` is installed on this machine. Authentication and the GitLab server version have not been checked.
- GitHub list pagination, comment counts, PR/commit checks and reference-status batches use provider-specific GraphQL queries. `fetchGithubRefStatus` merges issue/PR numbers and caches by repository + number, valid only because GitHub shares their numbering space. `batchRecheckAfter` selects the minimum per-item recheck interval; it does not enforce a request budget.
- Local `glab api --help` confirms both REST and GraphQL support. GitLab REST issue/MR lists support `iids[]`; GitLab pagination includes offset/Link headers, selected-resource keyset pagination and GraphQL cursors. Basic fields can be batched, while the REST baseline needs per-MR detail reads for CI and approvals. GitLab GraphQL is an optional batching optimization whose field/version support must be verified; it is not a promise to eliminate every detail request.

## Architecture

Keep plain Git independent of forge availability. Add GitLab behind the existing forge seam, extend the seam for the operations that currently bypass it, and route those callers through a shared resolver. Keep GitHub implementations and their default behavior intact. Preserve existing `/api/v1/p/:projectId/github/...` routes and response shapes for backward compatibility; the path is a historical API name, while the selected project determines the provider. All added wire fields belong in the Zod contract first.

Do not reintroduce `forge` or other project-bound fields into workspace health, including its WebSocket snapshot. Extend the project registry's provider contract and the project-scoped platform responses that actually carry identity/readiness. Audit `forgeInfoSchema`/`ForgeInfo` consumers independently: update a shared provider shape only where a current consumer needs it, without adding it to `healthResponseSchema`. Replace the task Git step's hard-coded GitHub identity with the selected project's actual provider. Keep the existing health omission assertions intact. Global CLI installation checks may report glab alongside gh; that is distinct from project-specific forge identity or authentication.

Follow the existing GitHub integration model: GitHub uses `gh`, and GitLab uses `glab`. GitLab platform operations, including automation, MR checkout metadata, comments, creation and merge, run through bounded glab subprocess calls, including `glab api` for REST endpoints. Specify the target instance explicitly, cap time/output and pagination, and validate returned JSON with Zod. Do not add a separate direct HTTP transport.

Reuse glab's existing authentication and instance configuration. cezar does not extract or manage Tokens, provide Token entry forms, or create a forge credential store. Missing glab, missing authentication, denied permissions and an offline instance disable only the affected platform features while Git remains usable. Project-scoped cached availability reads must not wait for a network probe; workspace health remains free of project forge detection.

Recognize gitlab.com directly. Discover self-managed instances from glab's configured hosts, reading only the host metadata needed for classification without exposing credentials or probing arbitrary Git remotes over the network. Respect glab's configured SSH-to-web/API mapping where transport and API hosts differ. Unknown hosts remain plain Git until configured in glab. Do not hard-code the motivating company domain and do not infer platform solely from the substring `gitlab`. Absence of glab or host metadata must not crash boot or make a Git repository appear to be missing.

## CLI availability and multiple platforms

- With Git installed but glab absent, registration, task worktrees, diffs, commits and push remain available using existing Git authentication. GitLab Issue/MR/CI features are unavailable, with a clear hint to install glab and authenticate against the relevant instance. Using IDEA does not imply that glab is installed or that its authentication is available.
- With glab installed but unauthenticated, preserve the same Git behavior and show an instance-specific login hint. Never automatically install glab or launch an interactive CLI login during server boot.
- With glab installed and authenticated, all supported GitLab platform flows use that CLI. Git SSH/HTTPS authentication and platform API authentication remain separate; report which operation failed accurately. Restricted credentials must not be represented as permission to write, and unreadable data must not become an empty successful result.
- GitHub and GitLab projects, including multiple self-managed GitLab instances, coexist in one workspace. Resolve the CLI and target host per operation from the project's selected remote; do not change a process-global active host. Revalidate cached discovery and availability after remote or CLI configuration changes.
- A repository with multiple remotes retains existing base-versus-push resolution. Use the base remote's provider and project for PR/MR operations and the push remote for Git push. If a cross-provider source/target combination cannot be represented by the target platform, return an explicit unsupported result rather than operating on the wrong repository.
- No new credential APIs, Token forms, managed credential files or CEZ environment flags are part of this design. glab handles instance protocol, API origin, authentication and certificate trust. Do not disable certificate verification or pass extracted secrets to another origin.

Preserve full namespaces and distinguish SSH transport ports from HTTP/API origins. Build browser links without URL credentials. Cache and identity keys include instance, full project path, item kind and item IID: GitLab issue #1 and MR !1 are different objects.

Treat full-path parsing as a compatibility-sensitive change to `ParsedRemote` and its consumer contract. Add an explicit full project path/namespace representation while preserving existing GitHub `owner`/`repo` meaning; do not silently redefine `owner` for all callers. Audit every parser/type consumer and every construction site: fork-parent lookup and remote selection (`git-remotes.ts`), resolver and browser links (`forge/index.ts`), fork PR arguments (`forge/github.ts`), dashboard identities (`workspace/dashboard-forge.ts`), automation checkout (`automations/pr-head.ts`), and the project/automation consumers in `server.ts`. Replace the existing nested-group expectation deliberately, add full-path tests, and retain assertions for GitHub fork targeting, push/base selection and credential stripping. Full namespace must propagate to API project IDs, links, cache keys and persisted references without truncation.

Include `parseOwnerName`, `resolveRepoHandle`, `resolveRepoHandleStrict`, their callers and repository-handle caches in that audit. These remain GitHub-specific; do not relax their two-part GitHub slug validation merely to accept GitLab namespaces. GitLab resolves its own full project path and numeric project ID. Audit every `gh api` `{owner}/{repo}` placeholder call: GitLab requests must name the explicitly resolved project rather than inherit an incidental worktree remote through CLI placeholder expansion.

## Provider mechanisms and contract mapping

### Queries, batching and request cost

Sharing the CLI integration model does not mean sharing GitHub API queries. Keep GitHub GraphQL documents and parsers inside the GitHub driver. GitLab uses its own REST endpoints through glab for the baseline implementation; glab also supports GraphQL, so using GitLab GraphQL for a demonstrated batching need remains compatible with this architecture. Any such query must use GitLab's schema and be verified against the supported self-managed versions rather than translated by field-name substitution.

For reference-status batches, split issue and MR IIDs first and use project-scoped `iids[]` list filters to obtain the fields those responses actually provide, with state/scope filters explicitly covering closed and merged items. Comment counts should use list-provided `user_notes_count` where available, not introduce one detail call per row. Request detailed CI jobs, approvals or missing merge metadata only when required by the visible surface or an explicit workflow action. Do not equate a list response with complete detailed merge eligibility.

The MR list endpoint does not supply `head_pipeline` for lazy CI hydration. Return `checks: null` at the list tier, matching GitHub's existing list behavior. Hydrate CI only for requested/on-screen MRs through single-MR/pipeline reads, and load detailed jobs only when needed. A null list glyph means not hydrated, not no CI. Count these detail calls in the operation's concurrency/request/deadline budgets; test that an initial list does not fetch one pipeline per MR and that visible-row hydration reuses cached/in-flight reads.

Public batch input limits are compatibility limits, not a promise of one upstream subprocess. Keep existing GitHub limits and behavior. The GitLab implementation plan must define numeric per-operation request/page caps, per-instance concurrency limits, a total deadline and response-size caps before its read paths are implemented. Verify upstream request/subprocess counts in fixture tests for cold, cached and partially failed batches. Do not launch an unbounded Promise.all over item IIDs. Deduplicate in-flight reads, cache by provider identity and apply throttling cooldown/Retry-After. Detailed operations that exceed their budget return the existing explicit unavailable/unknown or partial-data shape rather than silently claiming completeness; any needed additional wire signal is defined in the contract first.

Do not copy GitHub refresh intervals as an upstream request-cost policy. `batchRecheckAfter` only takes the minimum requested interval; GitLab rechecks must also honor its bounded request budget and instance cooldown. Missing CI or approvals due to permissions, timeout, unsupported version or budget exhaustion cannot become a passing/ready state. A REST request-count increase is a measured tradeoff to document and test, not a mandatory degradation accepted merely because the provider is GitLab.

### Item identity

GitLab never combines issue and MR IID lists into a single number Set. Deduplicate within each kind only. Keep issue and MR result maps independent even for the same IID. GitLab cache entries and in-flight keys include instance, full project identity, kind and IID, and mutations invalidate only the matching resource (plus dependent aggregates). GitHub may retain its existing shared-number optimization.

Audit `runs/task-refs.ts`, persisted task references, UI query/cache keys, URL parsing, automation receipts/deduplication and cache invalidation callers for the same distinction. Preserve GitHub references and recognize GitLab `/-/issues/:iid` versus `/-/merge_requests/:iid`; never infer kind from a trailing number alone. Add a regression where issue #1 and MR !1 coexist with different states through fetch, task persistence, rendering, refresh and mutation invalidation.

For standard GitLab Issue API responses, map `opened` to `open` and `closed` to the existing contract's `completed` category. GitLab does not provide GitHub's `stateReason: NOT_PLANNED`; this adapter must not emit `not-planned` or infer it from labels, comments or duplicate links. Here `completed` is the shared closed-state category, not proof that business work was completed; GitLab-facing copy should say Closed where that distinction matters. Preserve GitHub's existing completed/not-planned distinction. Test closed, reopened and duplicate-linked GitLab issues.

### Merge-state normalization

Retain the existing wire shape as a provider-neutral presentation model where its semantics fit; do not reuse `normalizeMergeState`, which consumes GitHub-specific inputs. Implement a separately tested GitLab normalizer with these rules:

| Contract field | GitLab meaning |
| --- | --- |
| `mergeable` | Confirmed conflict maps to `conflicting`; confirmed conflict-free mergeability maps to `mergeable`; unchecked, computing or unreadable signals map to `unknown`. Conflict-free does not imply policy eligibility. |
| `reviewDecision` | Required approvals satisfied maps to `approved`; required approvals missing maps to `review-required`; `changes-requested` requires an explicit supported blocking review signal, not an ordinary comment. Unreadable approval requirements map to `unknown`. An explicit absence of required reviews must not block merging merely because the provider has no GitHub-style review decision. |
| `checks` / `checksTier` | Readable job/check rows are `detailed`; only a readable pipeline rollup is `aggregate`; unreadable CI is `none` with a reason. Confirmed no configured CI is distinct from failure to read CI. |
| `methods` / `defaultMethod` | Derive only executable choices from project merge strategy and squash policy. GitLab fast-forward or semi-linear policy is not automatically the GitHub-style `rebase` operation. If the existing enum cannot represent an actual supported action faithfully, make an explicit additive contract/UI decision before implementing that action. Do not modify project policy to satisfy a requested method. |
| `eligibility` / `blockers` / `canMerge` | Normalize detailed merge status, draft/lifecycle, approvals, pipeline, unresolved discussions, branch/project policy and permission evidence. Unknown/unreadable mandatory evidence cannot produce `ready`; the server remains authoritative and revalidates at mutation time. |
| `canOverride` | Always `false` for this GitLab implementation; hide the override action in GitLab UI. Reject override requests server-side rather than silently ignoring them. Any future equivalent requires a separately specified, verified provider operation. |

Retain expected-head-SHA validation and the per-MR concurrent-merge guard. Version/tier differences must be covered by fixtures with explicit unknown/unavailable results. A contract extension must be additive and verified against both GitHub routes and UI consumers; do not widen types merely to suppress mismatched behavior.

For the independent `conflicts[]` reference-status axis, `has_conflicts: true` is explicit conflict evidence. Current GitLab documentation also defines `detailed_merge_status: conflict` as explicit conflict evidence; preserve that mapping for versions that return it rather than assuming every server has the same enum. Either returned signal may populate the list without another request. Treat older-version `broken_status`/`need_rebase` as potential conflict or a rebase requirement, not confirmed conflict by themselves. Checking/unchecked, an absent field, `cannot_be_merged` alone and `has_conflicts: false` without a completed mergeability check do not establish conflict-free state. List responses can include has_conflicts, but their mergeability computation may be stale. Revalidate through bounded single-MR reads when a merge panel or explicit action needs current evidence; unreadable/checking results remain unknown. Test both explicit conflict signals, older-version potential statuses, missing/false has_conflicts during checking, stale cached evidence and detail refresh. The UI must not render absence from conflicts[] as a confirmed clean merge; potential conflict remains unknown in the existing three-state contract, with explanatory blocker text where available.

### Automation review capabilities and approval snapshots

The baseline GitLab integration uses polling and has no inbound webhook receiver. It does not support the existing `pull_request.reviewed`, `pull_request.review_requested` or `pull_request.rereview_requested` triggers. Disable these choices with a provider-specific reason in the UI; validate create/update/enable/check/execute paths server-side so saved definitions or direct API calls cannot bypass the capability check. Existing unsupported definitions must remain readable but never silently become another trigger. GitHub review triggers remain unchanged.

GitLab does expose review-related webhook signals, including reviewer changes/re-requests and version-dependent review submission events. Those are not a replayable timeline for the existing poller. Adding webhook infrastructure or audit-event reconstruction is outside this implementation; do not claim GitLab has no review signals anywhere, and do not parse localized system-note text to fabricate equivalent events.

Provide a separately named GitLab approval-observed trigger through the automation contract and capability metadata, not by relabeling `reviewed`. Use `GET /projects/:id/merge_requests/:iid/approvals`, available on Free, and validate actual returned `approved_by` user identities and `approved_at` timestamps. This is a snapshot of currently retained approvals, not a complete approval/unapproval event log. Its supported guarantee is detection of approvals present at a successful poll; an approval granted and withdrawn between polls may be missed. Show that limitation in trigger help and distinguish individual approval from all required approval rules being satisfied.

That distinction is explanatory UI copy, not an all-rules-satisfied trigger condition. The approval-observed trigger depends only on individual approved_by identities/timestamps, never approvals_required, approvals_left, approval_rules_left or has_approval_rules. These additional fields differ by CE/EE edition; EE may expose them even without a paid license, so Free versus paid is not the same distinction. CE's approved boolean means at least one approval exists and must not be interpreted as proof that enterprise approval rules have been satisfied. Missing rule fields must not disable an otherwise valid individual approval snapshot. Merge eligibility is a separate capability assessment and retains the conservative rules above.

On enable or definition/source change, establish a successful current-state baseline without launching retained approvals. Persist deduplication by instance, target project, MR IID, approver ID and approval timestamp; replaying the same snapshot after a restart must not launch again. A later observed reapproval with a new timestamp is a new occurrence; disappearance/reappearance of the same timestamp is not. Never manufacture an event timestamp from MR updated_at or poll time. If the server version omits a required timestamp, mark this trigger unsupported with a reason. Failed/partial polls must not clear the baseline, mark approvals consumed or reset the enable boundary; retries must use the existing receipt/cursor discipline. A disabled interval never creates a backlog on re-enable.

Fixture acceptance includes unsupported review triggers across every mutation/execution entry point, Free-edition approval snapshots, first-enable baseline, repeat polling, restart, changed approval timestamp, revoked approvals, missed between-poll transitions, missing timestamps, partial failures and re-enable behavior. All approval detail reads obey the same per-instance request budgets as CI hydration. This intentionally narrows automation parity to reliable provider capabilities rather than promising GitHub event semantics from GitLab snapshots.

### Pagination and continuation tokens

Keep `issuesCursor`, `prsCursor` and returned next-cursor fields as opaque driver-owned continuation strings. They do not require GraphQL and must not be interpreted by shared callers as an offset or raw GitHub cursor. Existing GitHub token handling stays compatible. GitLab tokens encode and validate the selected endpoint's continuation, including page size/position where needed, and bind to instance/project, item kind and relevant query filters. Reject cross-project, cross-kind or incompatible-query token reuse.

GitLab REST endpoints may use page/per_page with X-Next-Page and Link, or keyset continuation where supported; GitLab GraphQL uses pageInfo/endCursor. Select the mechanism per endpoint and supported version. Do not assume that total/last-page headers always exist or that absence means page one. Validate continuation targets against the selected API origin/project and never follow arbitrary header-provided URLs with credentials. Preserve exact continuation when a caller limit stops partway through a page so items are neither skipped nor duplicated.

Use explicit bounded loops for lists, notes/timelines and automation reads rather than unrestricted CLI `--paginate`. Bound pages, records, bytes, requests and elapsed time; distinguish end-of-data from truncation or partial failure. Preserve automation high-watermark/tie-breaker deduplication separately from provider pagination tokens: an event cursor is not an API page number. Replacing GitHub's Link parser with GitLab's X-Next-Page parser alone is insufficient.

### Source/target projects and fork MRs

Resolve both the push/source project and base/target project to complete GitLab identities on the same instance, including full namespaces and numeric IDs. Do not reuse GitHub `--head owner:branch` formatting or `--repo host/owner/repo` assumptions. For a fork MR, submit source/target project and source/target branch according to the selected GitLab API/CLI operation's actual parameters, and verify the response identifies the expected pair. Duplicate lookup must compare both projects and branches, not source branch alone. Branch lookup, MR-head checkout and later updates must preserve that source/target distinction. Reject cross-instance/provider combinations that GitLab cannot represent. Cover same-project, fork, nested-group, same-named branches on distinct forks and target-default-branch cases.

## Functional parity and acceptance

| Existing user flow | GitLab equivalent and acceptance |
| --- | --- |
| Project registration, overview and Git actions | Repository remains recognized with glab absent; correct GitLab identity and links when host is known; existing Git auth, worktrees, diffs, commits and push work independently. |
| Issues/PR lists | Issues/MRs with labels, colors, authors, timestamps, drafts and bounded independent pagination. List partial failures must remain visible rather than masquerading as empty results. |
| Search and details | Search open/closed/merged items, descriptions, comments and corresponding timeline activity, bounded and normalized into the existing UI contracts. |
| Checks and reference badges | Lists return checks null; on-demand MR/pipeline/job hydration supplies CI within request budgets. Kind-separated issue/MR status caches, explicit conflict evidence, closed-issue mapping, refresh and post-mutation invalidation follow the rules above. Unreadable CI is unknown, never successful. |
| Task creation from a forge item | Preserve project and item identity, correct URL and full namespace; GitLab references survive persistence, reload and task rendering. |
| Draft creation and updates | Autosave and push through existing guards, then create/update an MR on the resolved target project; preserve branch and default-branch discovery, including master. Prevent duplicates on retries. |
| Branch lookup and changes | Find MR for a source branch; show bounded diffs, renames, binary/omitted patches and truncation; identify the diff head. |
| Merge panel and explicit merge | Reflect draft/conflicts/approvals/pipeline/permissions and actual project merge policy. Verify expected head SHA and preserve concurrency guards. Never auto-merge or bypass GitLab policy. |
| Workflow platform actions | MR update, issue/MR comments and CI waiting route to GitLab, including resumed runs. Existing workflows remain readable without renaming persisted GitHub-shaped keys. |
| Automations | Corresponding issue/MR creation, update, label, comment and lifecycle flows require provider-backed event evidence. GitHub review/review-request/re-review triggers are explicitly unsupported on the GitLab poller; approval-observed is a separate snapshot trigger with the limits above. MR head checkout, preview, deduplication, retry and bounded polling use GitLab identity. Existing automations never replay a backlog on upgrade. |
| Workspace dashboard | Recent creations and repository grouping use instance + full namespace; provider-appropriate names and links. |
| Navigation and tooling | GitLab/MR labels, links, glab installation/authentication status and actionable hints; English keys plus zh-CN translations, consistent project-aware gates across sidebar, palette and repository views. |
| Dry-run and compatibility | Network-free fixtures for both providers. Existing GitHub contracts, URLs, defaults and tests stay valid. |

Parity means equivalent cezar user flows, not inventing GitLab versions of GitHub-only platform policy. GitLab project merge strategy is server-controlled; offer only methods genuinely supported by that project. Tier/version-restricted approval or timeline data must explicitly degrade, not be fabricated or mapped to success. Platform mutations remain user/workflow-triggered; no real MR creation, comment or merge is required for verification.

1. Project provider contracts, compatibility-sensitive full-path remote parsing and consumer audit, self-managed discovery from glab configuration and provider selection. Do not add forge to health. With glab absent from PATH, assert that Git remains usable and platform operations degrade with installation hints; with glab authenticated, assert the full platform flow uses the correct instance.
3. Extend the driver for comments/checks/reference-status/update/comment operations; route every bypass listed in Current evidence, including task creation through existing `createPR`, changes through existing `prDiff`, and all five workflow nodes. Implement MR creation/update/comments/merge. Verify autosave/push errors, correct target/default branch, duplicate prevention, SHA changes, blocked policy, concurrent operations and continuation paths without real writes. Exercise route/workflow delegation for both providers so a working driver cannot conceal an unchanged GitHub-only caller.
4. Automation provider capabilities and checkout parity, including approval-observed contract/metadata and explicit rejection of unsupported review triggers. Preserve event high-watermark/tie-breaker, approval baseline/deduplication, bounded API pagination and enable-baseline guarantees. Verify every trigger against its actual signal source, approval snapshot limitations, fork project identity, missing pagination headers and restart/retry behavior. Do not build a webhook receiver or audit-event subsystem.
5. Project UI, task references, CLI installation/login hints, tooling, dashboard and translations. Verify GitHub/GitLab/plain-Git states, two self-managed GitLab hosts, and a workspace containing all three. Cover glab installed/authenticated, installed/unauthenticated and absent; absent glab must not hide Git actions or offer a non-existent Token connection flow.
6. Run repository gates in order: `npm run typecheck`, `npm test`, `npm run test:unit`, `npm run build`, `npm run test:package`. For browser changes, run the separate dry-run UI smoke suite and report skipped distinctly from passed.

Each behavior change starts with a regression that fails before its implementation. Existing user files and the untracked logs in this checkout are preserved. No new CEZ flag is planned. Any subsequently necessary environment contract change must update `.env.example` and `docs/reference.md` together.
