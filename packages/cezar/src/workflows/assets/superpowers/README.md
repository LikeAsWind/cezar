# cezar unattended v7

The workflow appears as `unattended` in the built-in catalog. **Skills → Superpowers updates**
can check official stable releases, stage a compatible candidate for review, activate it for new
tasks, or roll back. Automatic checks are optional and off by default; activation is always manual.
Every participating task pins its complete bundle in a private run lock, including helpers and
runtime assets. See `docs/reference.md` for storage, recovery and validation boundaries.

Superpowers 7 role nodes directly select their pinned original skill bodies or templates. The original vendor files, supporting scripts, hashes and licenses remain unchanged. Two explicitly custom roles are loaded directly: skills/project-probe/SKILL.md (requirements/repository/environment discovery) and skills/adjudicator/SKILL.md (evidence-based answers). Their research sources and evaluation scenarios are in docs/superpowers/research/.

`src/workflows/templates/unattended.ts` owns the three-tier graph and stage tasks and is registered in `src/workflows/templates.ts` alongside the other built-ins; context.md supplies shared unattended handoff constraints at the same instruction level as role content. There is no entry skill or adapter-reading chain. Supporting upstream helpers stay in the pinned vendor tree.

The built-in can be copied in the workflow editor and saved in `.ai/cezar/workflows/` as an ordinary project workflow. It has no private command/template placeholders. Portable `cezar workflow-action <action>` commands are bound to the current host installation by the common graph loader; original supporting review templates are read from the pinned skill directory. Built-in skill references still acquire a per-run Superpowers snapshot pin.

The target project's toolchain and setup/baseline/verify commands come from discovery. The shared host workflow actions perform real checks, freeze the validation plan, route complexity and seal the final diff. New graph templates use ordinary check nodes calling the host installation’s scripts/workflow-action.mjs; the same operations are available as cezar workflow-action <action>. Old snapshots retain their own runtime files; the source bundle no longer ships a duplicate runtime or artifact implementation. Delivery stops at cezar review without pushing or merging; quick-task remains the default.

All new workflow artifacts use `docs/superpowers/` and a persisted `YYYY-MM-DD-<topic>` prefix. Probe is `probe/<prefix>-probe.md`, its shared map is `probe/<prefix>-context-map.jsonl`, design is `specs/<prefix>-design.md`, and the plan is `plans/<prefix>-plan.md`. Environment, questions/answers, ledger, implementation, review, delivery, blocked reports, logs and verification receipts use the same prefix. Formal subagent reports are published under `logs/<prefix>-tasks/`; upstream helper scratch remains transient. The host derives a readable topic from the existing session titleSummary when available, falling back to the request title without another model call, assigns numeric suffixes on collision, and persists topic/date/prefix alongside runId in run.json. Every node receives the exact logical-name-to-path map from the host. Continue retains the original date, parallel runs have separate names, and topic/date are retained after title edits. No wildcard `.gitignore` is written into docs. Seal excludes only the current run's generated artifacts; other docs and code changes remain in its diff. Host-private trust and bundle pins stay in the existing `.ai/cezar/runs/` store.

New snapshots serialize the host template as `workflow.json`. The source assets in `src/workflows/assets/superpowers/` contain only roles, shared instructions, provenance and upstream files. The build copies them unchanged into `dist/workflows/assets/superpowers/` for publishing. Historical snapshot YAML and runtimes remain readable without being copied back into the source tree. Original upstream Superpowers files remain unchanged.

The original task lives once in CEZ_HANDOFF_FILE / ## Goal; no separate request snapshot is generated. Probe is discovery only. The host initializes its isolated context, gives it a thirty-minute wall-clock limit and permits Read/Glob/Grep, writes to the four discovery artifacts, and the exact host-controlled version-query command (15 seconds each). Compilation, tests, dependency setup, arbitrary shell, source writes, delegation and private MCP tools are unavailable. Independent reads and selected-tool version queries may be issued in batches of at most three native tool calls; same-file report writes are serialized and no subagents are spawned. Claude currently enforces this policy; a different probe backend is rejected explicitly instead of ignoring the boundary. Implementation/review nodes retain their backend selection. Already saved artifacts survive interruption; incomplete reports never mean ready.

Artifacts use the sibling directories `docs/superpowers/probe/`, `specs/`, `plans/` and `logs/`, with `YYYY-MM-DD-<topic>-<name>` filenames. Discovery stays in `probe/`; official design and plan locations stay in `specs/` and `plans/`. Other workflow reports and command logs use `logs/`; task/subagent reports use `logs/<prefix>-tasks/`. Only this layout is read. Host discovery lists Java/Maven locations from environment/PATH evidence and sibling JDK folders without a recursive machine scan. Grep requires a concrete file/module path and external Glob is denied. Save partial probe/map evidence when a real source entry is confirmed, then update incrementally; there are no timed progress reminders. The thirty-minute hard timeout and final artifact validation remain authoritative.

Validation commands can reference a unique `toolchains[].name` via `toolchain`. That toolchain's `execution` binds an observed absolute `javaHome` and/or absolute `pathEntries`. The host applies the same child JAVA_HOME/PATH to setup, version checks, baseline and verification, with no global environment modification. Java/Maven/Gradle commands require a Java home; missing tools or version mismatch block rather than fall back to the inherited Java. Keep repository Maven toolchains, compiler and test-runtime constraints, with matching version checks for each binding. Source/target alone does not establish the required Maven JDK.

Initial complexity routing runs as a host command followed by a built-in condition, without an agent session. The command writes route.json; fast enters planning directly, while standard/deep enter design and retain their selected tier for later execution. Routing failure ends at the blocked report.

Deep risk and SDD execution are separate. The planner records actual task dependencies and observed dispatch capability in execution-input.json. A host command writes execution.json: independent tasks plus an observed available tool select SDD; otherwise deep uses native execution with the risk constraints, final verification and independent review intact. Unknown capability never means a fabricated dispatch.

The host validates required stage artifacts, existing worktree paths in the map, and each pending Q-number/origin before accepting the corresponding success verdict. It keeps its own validation-plan and verified receipt in `.ai/cezar/runs/<runId>.unattended.json`; edits to worktree copies cannot weaken checks. This prevents accidental edits, not hostile code running under the same operating-system account. Old runs without this trusted baseline cannot silently acquire trust from a mutable worktree copy.

An explicitly requested, isolated product-test failure can be accepted as a baseline only with the observed exit code, product-specific output fragments, complete normalized output SHA256 and reproduction reason in expectedFailure. Additional failure output or nondeterministic output blocks. Original nonzero results remain visible; final verification forbids expectedFailure and requires passing commands.

Continue on a failed managed workflow re-enters its saved graph, preserves the original bundle and loop budgets, and persists user additions in the existing message queue and run history. It does not create a standalone continue-N chat. Review/delivery/seal blockers return through verification. An invalid recovery point is an error; exhausted automatic budgets are never replenished. After adjudication, the caller preferentially resumes its own session, while builder and final reviewer remain independent; unsupported backends or changed launch accounts use file recovery.

Design, planning, execution and repair can send one question.md to the same adjudicator node when needed. The question records its origin; the answer returns to that caller. clarification.md preserves questions, evidence, uncertainty and machine rulings across fresh backend sessions. The shared loop allows at most eight answers per run, including design revisions and later stages. A clear fast task does not need to call the role. Missing material product intent blocks instead of becoming an invented preference. Independent reviewers remain separate; adjudication cannot remove findings or weaken checks.

External technical facts are researched through available web tools when uncertain, using primary sources for the target version. No browsing capability is installed by a prompt: unavailable tools or failed searches must be reported honestly. Static wiring/graph tests and prompt review are not evidence that every model will follow these instructions; the research notes contain behavioral scenarios for evaluation.

Probe scope: turn a vague request into an evidence-backed impact background and a reusable context-map.jsonl (path, responsibility, request relevance, symbols, dependencies and confidence). It preserves unknowns and does not generate acceptance criteria. Downstream roles locate files through this map instead of repeating a full tree traversal; they reread relevant source and update specific stale/missing entries. Environment and validation-plan artifacts remain required host inputs.


Version-aware validation: toolchains records targetVersion/buildVersion/runtimeVersion separately for each named toolchain/module, with source evidence and constraints. Unknown versions are null. environmentChecks contains observed executable checks plus expectedOutput fragments, using the existing structured command fields and kind check. A nonempty toolchains list requires environment checks. The baseline freezes both arrays in validation-plan.json after probe; setup runs before these checks, and every final verification reruns them before compiling/testing. A zero exit code without all expected fragments still fails. baseline.json / verify.json embed environment.checks with actual output, including missing executable/cwd failures. Successful version-query logs are removed; failures retain diagnostic logs.

The host verifies observed version markers, not arbitrary cross-language compatibility semantics. Planning and implementation must consume the frozen constraints, and the repository's compilation/test/compatibility commands must enforce the target. A newer JDK with source/target flags alone does not prove older Java API compatibility, nor does a test on a newer runtime prove behavior on the target deployment runtime. Existing legacy plans without these arrays keep their previous behavior.
